# 存储优化方案：细粒度操作

## 当前实现的问题

### 现状
```javascript
// 当前做法：全量替换
1. 读取整个数组到内存
2. 修改内存中的数组
3. 保存整个数组回存储
```

### 问题分析
- **性能问题**：每次操作都要序列化/反序列化整个数组
- **数据量大时**：30,000 条记录 ≈ 8MB，每次保存都要处理全部数据
- **并发问题**：多个操作可能冲突
- **内存占用**：始终在内存中保持完整数组

## Chrome Storage API 的限制

### 本质限制
Chrome Storage 是**键值对存储**，不支持：
- ❌ 部分更新（partial update）
- ❌ 增量更新（incremental update）
- ❌ 数据库式的查询和更新
- ❌ 事务支持

## 优化方案

### 方案:使用 IndexedDB

#### 思路
使用 IndexedDB 替代 Chrome Storage，支持更细粒度的操作。

#### 实现示例
```javascript
// 打开数据库
const db = await openDB('readingLinks', 1, {
  upgrade(db) {
    const store = db.createObjectStore('links', { keyPath: 'id' });
    store.createIndex('url', 'url', { unique: true });
    store.createIndex('timestamp', 'timestamp');
  }
});

// 添加链接（只写入一条）
async function addLink(link) {
  const tx = db.transaction('links', 'readwrite');
  await tx.store.add({
    id: Date.now(),
    ...link
  });
}

// 删除链接（只删除一条）
async function deleteLink(id) {
  const tx = db.transaction('links', 'readwrite');
  await tx.store.delete(id);
}

// 更新链接（只更新一条）
async function updateLink(id, updates) {
  const tx = db.transaction('links', 'readwrite');
  const link = await tx.store.get(id);
  await tx.store.put({ ...link, ...updates });
}

// 搜索（使用索引）
async function searchLinks(keyword) {
  const tx = db.transaction('links', 'readonly');
  const index = tx.store.index('timestamp');
  const allLinks = await index.getAll();
  
  // 在内存中过滤（或使用游标）
  return allLinks.filter(link => 
    link.title.includes(keyword) || 
    link.tags.includes(keyword)
  );
}
```

## 实施建议

1. **添加防抖保存**
   ```javascript
   // 快速连续操作时，延迟保存
   const debouncedSave = debounce(saveLinks, 500);
   ```

## 总结

- 5MB 完全可以使用 IndexedDB
- 容量不是问题（IndexedDB 容量远大于 Chrome Storage）
- 即使数据量不大，IndexedDB 在性能、可靠性和查询能力上仍有优势
- 建议：如果追求更好的可靠性和性能，可以迁移到 IndexedDB
