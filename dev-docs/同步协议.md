# 背景
假设有class X{ int a, string b, text c, create_time, update_time },它是一个业务主体建模，单个平均也就200个字符，然后我有手机端，电脑端等，以新增为主，每个端都有很多这样的X对象的实例列表，可以手动同步或者定期同步，我想设计一个一致性同步协议，我想采用类似于git的设计思路，


整体的架构，终端设备可能有，手机1，手机2，电脑1，平板等，然后还有一个用于同步的服务器，当然，这些理论上都是 peer关系，也就是对等的，只是因为服务器是专门online接受同步服务的而已

## 2. 内容指纹 (Hash)
Git 的核心是“内容寻址”。如果两个设备上的对象 X 内容完全一样，它们的指纹必须一样。

**设计推演：**
我们在对象 X 里增加一个字段 `hash`。
*   **算法**：`hash = SHA256(id + content)`
*   **作用**：同步时，手机1告诉服务器：“我有 `uuid-1234`，它的指纹是 `abc...`”。服务器一看：“巧了，我这也是 `abc...`，那就不用传了，省流量！”

在分布式系统里，**“先后顺序”不是由“几点几分”决定的，而是由“因果关系”决定的。**

我们要维护一个 **操作日志**，而不是只存最终的数据对象。

每个操作日志（Log）长这样：

```json

{
  "op_id": "op-001",           // 这次操作的唯一ID
  "device_id": "phone-1",      // 谁干的
  "parents": ["op-000"],       // 关键！这个操作是基于哪个操作之后的？
  "changes": [                 // 具体的变更内容
     { "target_id": "uuid-1234", "action": "new|update|delete", "hash": "xyz...", "data":{} }
  ]
}

```
## 3. 历史合并方法：提交历史合并方法

**场景 A（线性发展）**：

*   手机1 创建 X1，生成 `op-1`，`parents: []` (它是老祖宗)，推送给服务器

*   手机1 修改 X1，生成 `op-2`，`parents: ["op-1"]` (我是 op-1 的儿子)

*   同步给服务器：服务器一看，`op-2` 的爸爸是 `op-1`，我有 `op-1` 吗？有。好，那我接受 `op-2`。


**场景 B（并行发展 - 冲突的诞生）**：

*   手机1 离线创建 X1 (`op-1`, parents: `[]`)。

*   手机2 离线创建 X2 (`op-2`, parents: `[]`)。


手机1先推送，服务器上是最新的手机1的版本

手机2晚推送，它并不知道手机1已经先推送了，服务器发现它的提交版本已经不对了，拒绝推送。

手机2 把最新的历史拉下来，在本地合并，发现X1的内容已经被修改，出现了冲突，要求手动合并冲突，用户在手机2上合并了冲突，比如选择某一个版本保留，然后推送。

服务器上继续保持最新的版本。


## 4. 3的具体细化：对象合并方法：纯粹的新增（无冲突）

在历史合并的基础上，检查具体的修改日志里内容

即changes字段

"changes": [                 
    // 具体的变更内容
    { "target_id": "uuid-1234", 'action': 'new' ,"hash": "xyz...", "data":{} }
]

场景：无冲突

*   手机1 新增 X1, 推送到服务器，服务器收到 X1，ID 是 `uuid-A`，库里没有 `uuid-A`，**直接存**。
*   手机2 新增 X2，，从服务器拉取，获得X1对象，手机2继续新增X1对象，推送到服务器。
*   服务器收到 X2， ID 是 `uuid-B`。库里没有 `uuid-B`，**直接存**


场景：有冲突

假设手机1和手机2都拿到了 X1，都离线修改了它。

*   手机1 把 X1 改为 "内容A"，生成 `op-3` (parent: `op-1`)，推送到服务器
*   手机2 把 X1 改为 "内容B"，生成 `op-4` (parent: `op-1`)，推送到服务器之前，从服务器拉取，发现冲突
*   手机2 处理冲突，手动把 X1 修改为 内容A 和 内容 B的合并
*   手机2 推送最新的结果到服务器

# 6 完整的过程例子

#### 第一步：客户端发起“握手”（请求更新）
客户端（比如手机）连上服务器，喊“给我最新的”。
*   **手机说**：“服务器，我现在的最新版本号（或锚点）是 `v15`， 我上次从你这里更新是 `V10`。你有更新的吗？”

#### 第二步：服务器下发差异（增量拉取）
*   **服务器说**：“我有更新的，最新是 `v20`。这是 `v11` 到 `v20` 的操作日志（OpLog），你拿去。”
*   **手机做**：下载这些日志，在**本地数据库**里回放、合并。
    *   如果有冲突（比如服务器改了 X1，我也改了 X1），手机在本地生成“冲突副本”（如我们之前讨论的 `X1 (Conflict)`）。
    *   此时，手机的数据状态在逻辑上已经和服务器**对齐**了（都是基于 `v20`）。

#### 第三步：客户端本地合并与提交（本地 Commit）
用户在手机上看着刚刚同步下来的数据（包括可能的冲突副本），进行手动处理或继续新增。
*   处理完后，手机生成新的操作日志，比如 `v21`（基于 `v20`）。

#### 第四步：客户端推送（原子推送）
*   **手机说**：“服务器，我已经更新到 `v20` 了。现在我要上传我的新操作 `v21`，它的父版本是 `v20`。”
*   **服务器校验**：
    *   服务器检查：`v21` 的父版本确实是 `v20` 吗？
    *   如果是 -> **接受**，服务器版本变为 `v21`。
    *   如果不是（比如手机撒谎，或者网络延迟导致服务器已经变成 `v22` 了） -> **拒绝**。

# 7 优点

1. 手动处理冲突的优点：彻底杜绝“静默覆盖”

如果不遵循这个思路（比如允许直接上传），就会出现：
*   手机基于 `v10` 上传修改 -> 服务器变成 `v11`。
*   电脑基于 `v10` 上传修改 -> 服务器变成 `v12`。
*   **结果**：后上传的把先上传的覆盖掉了，而且没有任何提示，数据直接丢失。

思路：
*   手机必须先拉取电脑的修改，在本地看到冲突，解决后，才能上传。
*   **结果**：数据绝对安全，冲突一定会被发现。

2. 服务器逻辑极简（无状态化）
服务器不需要维护复杂的会话，也不需要去猜客户端的状态。
服务器的逻辑只有一句话：**“我只接受基于我最新版本（或我认可的版本）的更新。”**
这使得服务器非常容易扩展，哪怕有 100 台服务器，只要它们共享同一个数据库，逻辑都是一样的。

3. 冲突解决在客户端（用户体验好）
冲突解决是一个**重交互**的过程（需要用户看内容、选版本）。把这个压力放在客户端是合理的。服务器只负责存数据，不负责帮用户做决定。

## ⚠️ 唯一需要注意的“坑”：并发推送

虽然这个思路很好，但在极端情况下（比如手机和电脑同时点击“同步”按钮），还是会遇到 Git 经典的报错：

**场景：**
1.  手机和电脑都拉取了 `v20`。
2.  手机处理完，推送 `v21` -> **成功**。服务器现在是 `v21`。
3.  电脑处理完，推送 `v21'` (基于 `v20`) -> **失败！** 服务器拒绝，因为服务器已经是 `v21` 了，电脑的版本老了。

**解决方案（重试机制）：**
电脑收到“拒绝”后，不能傻掉，必须自动触发**“重试流程”**：
1.  自动再次拉取服务器的最新 `v21`。
2.  在本地合并 `v21` 和电脑的修改。
3.  生成 `v22`。
4.  再次推送 `v22`。


# opLog的ID设计规则

在这个架构中，op_id（操作ID）不应该是一个简单的自增数字（如 1, 2, 3），而应该是一个 Hash 码（通常称为 Digest 或 Checksum）。

这不仅是“最好”，而是实现 Git 风格同步的核心必要条件。

以下是为什么要这样做的深度推演：

数据完整性校验 (防篡改)

Hash 码不仅仅是 ID，它还是一个指纹。

当你收到一个 opLog，它的 ID 是 hash_123。你可以通过重新计算这个日志的内容来验证它是否被篡改或损坏。
验证公式：计算 SHA256(操作内容) == op_id
如果相等，说明这个操作日志是完整、真实的。
如果不等，说明数据在传输中坏了，或者被恶意修改了。

去重与幂等性

在网络不稳定的情况下，手机可能会重复发送同一个操作（比如超时重试）。

场景：手机发送了操作 abc...，服务器收到了。手机没收到确认，又发了一次 abc...。
处理：服务器一看，“abc... 这个 ID 我已经有了”，直接忽略第二次请求。
优势：不需要复杂的逻辑判断，只要 ID（Hash）存在，就代表操作已执行。

🛠️ 具体实现建议

在这个设计中，op_id 的生成公式应该是：

op_id = text{SHA256}( text{device_id} + text{timestamp} + text{parent_hash} + text{content_hash} )

device_id: 谁干的（防止不同人生成相同时间戳）。
timestamp: 什么时候干的。
parent_hash: 基于谁干的（这是形成 Git 链条的关键）。
content_hash: 干了什么（具体的业务数据变更）。


# 技术路线的判断

操作日志里所谓的“分离存储”（Git 的做法）主要是为了解决“大文件”和“极致去重”的问题。对于你目前的业务场景（文本为主，单条 200 字符），直接存不仅没问题，反而能降低系统复杂度。

这就导致了两次网络请求（一次传数据，一次传日志），而且服务器端需要维护两套存储系统（一套存日志数据库，一套存文件对象）。

对于文本（200字符）：去重收益极低，直接存更简单。
对于二进制/大文件：去重收益巨大，必须分离存。

如果决定为了支持未来的二进制文件而采用“分离存储”，那么这些对象（Blob）通常采用 Key-Value 存储 或 对象存储 的方式。

目前还是直接在日志里存完整的单条内容即可。
