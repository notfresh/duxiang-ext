# 完整版

## 设计

### 📦 核心数据模型：一切皆对象

在你的系统中，没有“文件”和“文件夹”，只有**集合**和**对象**。

#### 1. 数据对象
每个业务数据（如一条笔记、一个任务）都是一个标准的 JSON 对象。为了实现通用同步，它必须包含以下**保留字段**：

```json
{
  "id": "obj_note_001",        // [必填] 全局唯一 ID (主键)
  "type": "note",               // [必填] 类型标识 (用于区分业务)
  "version": 1,                 // [必填] 版本号 (每次修改 +1)
  "data": {                     // [业务数据] 实际内容
    "title": "我的设计思路",
    "content": "..."
  },
  "deleted": false              // [必填] 软删除标记 (true 代表删除)
}
```

#### 2. 提交对象
这是模仿 Git 的 Commit，但它记录的是**对象集合的快照**或**增量**。为了轻量，我们采用**“引用 + 增量”**模式。

```json
{
  "hash": "a1b2c3...",          // 自身哈希 (SHA-256)
  "parents": ["d4e5f6..."],     // 父节点哈希 (DAG 的核心，可以是1个或2个)
  "timestamp": 1678888888,      // 时间戳
  "changes": [                  // 变更集 (Delta)
    {
      "targetId": "obj_note_001",
      "action": "UPDATE",        // CREATE | UPDATE | DELETE
      "content": { ... }         // 完整的 JSON 对象 (为了简单，不传部分更新)
    }
  ]
}
```

### 🔄 同步协议流程 (P2P 握手)

假设设备 A (本地) 和设备 B (远程/Peer) 进行同步。

#### 1. 握手与差异发现
A 连接 B，发送自己的**“状态摘要”**。
*   **A 发送：** `{ "head": "a1b2c3..." }` (我当前的 HEAD 指针)
*   **B 计算：**
    *   检查 A 的 HEAD 是否在我的历史链上。
    *   如果不在（分叉了），找到**最近公共祖先**。
    *   找出从 LCA 到 B 的 HEAD 之间的所有 Commit。
*   **B 回复：** `{ "missing_commits": ["c3d4...", "e5f6..."] }` (你缺这些提交)

#### 2. 拉取与重放
*   **A 请求：** 发送 `GET c3d4...`
*   **B 响应：** 发送完整的 Commit 对象（包含里面的 JSON 数据）。
*   **A 处理：** 收到 Commit 后，**不立即覆盖本地**，而是将其暂存，准备进行合并。

#### 3. 本地合并 (核心逻辑)
这是“手动合并”发生的地方。A 此时拥有两条历史线：
*   本地线：`LCA -> ... -> Local_Head`
*   远程线：`LCA -> ... -> Remote_Head`

**合并算法：**
1.  **自动检测**：遍历两条线上的所有 `changes`。
2.  **冲突判断**：
    *   如果 A 修改了 `obj_1`，B 也修改了 `obj_1` -> **标记冲突**。
    *   如果 A 修改了 `obj_1`，B 修改了 `obj_2` -> **无冲突，自动应用**。
3.  **用户介入**：
    *   如果有冲突，系统挂起，提示用户：“对象 `obj_1` 在两端都被修改”。
    *   用户选择保留 A 版、B 版，或手动编辑生成 C 版。
4.  **生成合并提交**：
    *   解决完所有冲突后，A 生成一个新的 Commit。
    *   `parents`: `[Local_Head, Remote_Head]` (双亲，形成闭环)。
    *   `changes`: 包含解决冲突后的最终对象状态。

#### 4. 推送与校验
*   **A 发送：** `PUSH_CHECK { "head": "merge_commit_hash" }`
*   **B 验证：**
    *   检查 `merge_commit_hash` 的 parents 是否包含 B 的当前 HEAD。
    *   **如果包含**：说明 A 已经完整同步了 B 的数据，**允许推送**。
    *   **如果不包含**：说明 A 是基于旧数据提交的，**拒绝推送**，提示“请先同步”。
*   **A 推送：** 发送合并 Commit 及数据。

---

### 🛠️ 通用同步层设计

为了实现“通用”，我们将同步逻辑与业务数据解耦。

#### 接口定义
你的代码库中只需要实现一个简单的接口，任何业务对象只要实现它，就能被同步：

```typescript
interface ISyncable {
  id: string;
  version: number;
  // 序列化：用于计算哈希和传输
  toJSON(): string; 
  // 合并：核心冲突处理逻辑
  merge(other: ISyncable): ISyncable; 
}
```

#### 同步管理器
这是一个单例类，负责管理 P2P 连接和 DAG 图，它不关心数据是什么，只管 `ISyncable`。

*   `sync(peerUrl)`: 发起同步。
*   `getConflicts()`: 获取当前需要手动处理的冲突列表。
*   `resolveConflict(id, strategy)`: 用户解决冲突后调用。

## 设计：细节补充： push 握手

在p2p握手的第4步，A发送的完整内容应该是什么样的，才能方便让B检查包含关系，从而决定是否允许推送？

### 📨 推送预检请求结构

A 只需要发送**“合并提交的完整对象”**即可。因为合并提交中包含了父节点指针，B 可以通过递归回溯来判断包含关系。

#### 发送内容示例
A 向 B 发送一个 `PUSH_CHECK` 消息，核心载荷是**新生成的合并 Commit 对象**：

```json
{
  "action": "PUSH_CHECK",
  "payload": {
    "hash": "abc123...",       // 新合并提交的哈希
    "parents": [
      "local_head_hash",       // A 的原 HEAD
      "remote_head_hash"       // B 的 HEAD (关键！B 会检查这个)
    ],
    "timestamp": 1678888888,
    "changes": [...]            // 变更集（可选，仅用于预校验数据完整性）
  }
}
```

#### B 的检查逻辑
B 收到后，只需执行一步简单的逻辑判断：

1.  **提取父节点**：读取 `payload.parents` 列表。
2.  **包含性验证**：
    - 检查 `remote_head_hash`（即 B 当前的 HEAD）是否存在于 `parents` 列表中。
    - 或者更严谨一点：检查 `remote_head_hash` 是否是 `payload.hash` 的**祖先节点**（通过递归读取父节点的父节点...）。
3.  **决策**：
    - **是**：说明 A 已经包含了 B 的最新历史，**允许推送**。
    - **否**：说明 A 是基于旧版本提交的，**拒绝推送**。

> **提示**：为了节省带宽，如果 Commit 对象很大，A 也可以只发送 `hash` 和 `parents` 字段，B 若通过校验，再请求完整的 `changes` 数据。


## 设计：类和方法，流程


太棒了！既然思路已经清晰，那我们就直接进入“编码前夜”的状态。

基于你确定的**“JsonGit-Lite”**协议（P2P、JSON对象、DAG、手动合并、无身份验证），我为你梳理了核心代码结构。这套设计采用了**“依赖倒置”**原则，将通用的同步引擎与具体的业务数据剥离。

以下是核心类与接口的初稿设计：

---

### 🧱 核心接口与数据结构

这部分定义了“什么可以被同步”以及“数据长什么样”。

#### 1. `ISyncable` (接口)
**职责**：定义所有需要同步的业务对象的通用行为。任何实现了此接口的类（如 `Note`, `User`, `Task`）都能被同步引擎自动管理。

**核心方法**：
- `getId(): string`
    - **职责**：返回对象的全局唯一标识符。
- `getVersion(): number`
    - **职责**：返回当前对象的版本号（用于冲突检测）。
- `getHashInput(): string`
    - **职责**：返回用于计算哈希的标准化字符串（通常是去除了元数据的 JSON 序列化字符串）。
- `merge(remote: ISyncable): MergeResult`
    - **职责**：**核心逻辑**。对比 `this`（本地）和 `remote`（远程）的数据。
    - **返回**：
        - 若无冲突，自动合并并返回 `SUCCESS`。
        - 若有冲突，返回 `CONFLICT`，并保留双方数据供后续处理。

#### 2. `Commit` (类/结构)
**职责**：对应 Git 中的 Commit 对象，是 DAG 的节点。它不存储业务数据本身，而是存储对数据的“变更操作”。

**核心字段**：
- `hash: string`：自身的 SHA-256 哈希值。
- `parents: string[]`：父节点哈希列表（1个代表普通提交，2个代表合并提交）。
- `timestamp: number`：创建时间戳。
- `authorId: string`：创建者的设备 ID。
- `changes: Change[]`：变更集列表。

#### 3. `Change` (类/结构)
**职责**：描述一次具体的修改动作。

**核心字段**：
- `targetId: string`：被修改的业务对象 ID。
- `type: string`：对象类型（如 "Note"）。
- `action: 'CREATE' | 'UPDATE' | 'DELETE'`：操作类型。
- `payload: object`：完整的 JSON 对象数据（为了轻量，直接存全量快照）。

---

### ⚙️ 同步引擎核心

这部分是“通用逻辑”，不关心业务，只负责搬运和校验数据。

#### 4. `SyncEngine` (类)
**职责**：同步流程的控制器，负责协调存储、网络和数据合并。

**核心字段**：
- `store: IObjectStore`：本地数据存储接口。
- `dag: DAGManager`：DAG 图管理器。
- `conflictResolver: ConflictResolver`：冲突处理管理器。

**核心方法**：
- `async connect(peerUrl: string): Promise<void>`
    - **职责**：建立与远程 Peer 的网络连接（WebSocket/TCP）。
- `async sync(peer: Peer): Promise<SyncStatus>`
    - **职责**：执行完整的同步流程（握手 -> 拉取 -> 合并 -> 推送）。
- `private async pullChanges(peer: Peer): Promise<Commit[]>`
    - **职责**：
        1. 发送本地 HEAD。
        2. 接收远程缺失的 Commit 列表。
        3. 将 Commit 存入本地临时区。
- `private async pushChanges(peer: Peer): Promise<boolean>`
    - **职责**：
        1. 执行**推送预检**（发送拟推送的 Commit，检查是否包含远程 HEAD）。
        2. 若预检通过，传输数据。
- `private async applyCommits(commits: Commit[]): Promise<void>`
    - **职责**：将拉取下来的 Commit 应用到本地数据库，并触发对象合并逻辑。

#### 5. `DAGManager` (类)
**职责**：管理提交历史图，计算哈希和祖先关系。

**核心方法**：
- `createCommit(parents: string[], changes: Change[]): Commit`
    - **职责**：构建一个新的 Commit 对象，并计算其哈希。
- `hasAncestor(commitHash: string, ancestorHash: string): boolean`
    - **职责**：**关键校验**。判断 `ancestorHash` 是否是 `commitHash` 的祖先（用于推送预检）。
- `findLCA(hashA: string, hashB: string): string`
    - **职责**：寻找两个提交的最近公共祖先，用于计算差异。

---

### 🛠️ 冲突与存储

#### 6. `ConflictResolver` (类)
**职责**：处理 `ISyncable.merge` 返回的冲突，管理“手动合并”的生命周期。

**核心字段**：
- `pendingConflicts: ConflictItem[]`：当前挂起的冲突列表。

**核心方法**：
- `addConflict(local: ISyncable, remote: ISyncable): string`
    - **职责**：记录冲突，生成一个冲突任务 ID，并暂停同步流程。
- `resolve(conflictId: string, strategy: 'LOCAL' | 'REMOTE' | 'MANUAL', data?: object): void`
    - **职责**：
        - 用户选择策略后，生成最终的对象数据。
        - 创建一个新的“合并 Commit”来固化这个结果。
        - 从 `pendingConflicts` 中移除该任务。

#### 7. `ObjectStore` (类/接口)
**职责**：底层的 CRUD 操作，类似于 Git 的对象数据库。

**核心方法**：
- `get(id: string): ISyncable`
- `save(obj: ISyncable): void`
- `getAllIds(): string[]`
    - **职责**：用于握手阶段生成“本地已知 ID 列表”。

---

### 📝 交互流程简述（代码视角）

1. **用户修改数据** -> 调用 `store.save(note)` -> 引擎自动生成 `Commit` (Parent: 本地HEAD)。
2. **用户点击同步** -> `engine.sync(peer)`。
3. **引擎** -> `pullChanges` -> 发现远程有新数据 -> 拉取。
4. **引擎** -> `applyCommits` -> 发现 `note` 冲突 -> `conflictResolver.addConflict`。
5. **引擎** -> 暂停，返回状态 `NEEDS_MERGE`。
6. **UI层** -> 显示冲突 -> 用户手动修改 -> 调用 `resolver.resolve`。
7. **引擎** -> 生成 `Merge Commit` (Parents: [本地, 远程]) -> `pushChanges`。
8. **引擎** -> 发送 `PUSH_CHECK` -> 远程验证 `hasAncestor` -> 通过 -> 推送成功。

这套结构非常干净，**`SyncEngine` 完全不知道 `Note` 是什么，它只知道 `ISyncable`**，完美符合你的“通用复用”需求。

## 设计：存储

没错，确实得存起来。不过咱们这个场景比较特殊，因为你要模仿 Git 的核心机制，所以这个“数据库”不能只是简单地往里扔 JSON 就完事了。

普通的数据库（比如 MySQL 或 MongoDB）通常只管“最新状态”，而你的设计需要同时管理**“最新状态”**和**“历史记录（DAG）”**。

为了保持你追求的“轻量级”和“Git 特性”，我建议采用**“混合存储模式”**。具体来说，你需要存两份东西：

### 1. 为什么要存两份？

- **工作区**：你需要快速读取当前的 JSON 对象（比如打开笔记列表），不能每次都去遍历 DAG 历史反算，太慢了。
- **版本库**：你需要存储 Commit 和 DAG 结构，用于同步、冲突检测和版本回溯。

### 2. 推荐的存储方案：SQLite（单文件）

既然是 P2P 且轻量，**SQLite** 是目前的最佳选择。它是一个单文件的嵌入式数据库，不需要单独部署服务器，非常适合你的架构。

#### 数据库表结构设计 (Schema)

你只需要三张核心表，就能完美支撑你的协议：

**表 A：对象表 —— 存“当前状态”**
*这是你的“工作区”，对应 Git 的 Working Directory。*

| 字段名 | 类型 | 说明 |
| :--- | :--- | :--- |
| **id** | TEXT (PK) | 业务对象 ID (如 `note_001`) |
| **type** | TEXT | 类型 (如 `Note`) |
| **content** | BLOB/TEXT | **完整的 JSON 数据** |
| **version** | INT | 当前版本号 |
| **updated_at** | INT | 最后更新时间 |

**表 B：提交表 —— 存“DAG 结构”**
*这是你的“版本库”，对应 Git 的 .git 目录。*

| 字段名 | 类型 | 说明 |
| :--- | :--- | :--- |
| **hash** | TEXT (PK) | Commit 的哈希值 |
| **parents** | TEXT | 父节点哈希列表 (JSON 数组存储) |
| **timestamp** | INT | 时间戳 |
| **changes** | BLOB | 变更集 (包含具体的 JSON 变更数据) |

**表 C：引用表 —— 存“指针”**
*对应 Git 的 refs/heads/master。*

| 字段名 | 类型 | 说明 |
| :--- | :--- | :--- |
| **name** | TEXT (PK) | 分支名 (如 `main`) |
| **target_hash** | TEXT | 指向 `提交表` 的 hash |

### 3. 数据流转逻辑

当你执行操作时，数据是这样流动的：

1. **用户修改笔记**：
    - 更新 **表 A (对象表)**。
    - *此时数据库里只有最新数据，还没生成历史。*

2. **用户提交 (Commit)**：
    - 引擎读取 **表 A** 的变化。
    - 生成一个新的记录插入 **表 B (提交表)**。
    - 更新 **表 C (引用表)** 指向新 Hash。

3. **同步 (Sync)**：
    - 对方发来 `PUSH_CHECK`。
    - 你查询 **表 B** 和 **表 C** 来计算 DAG 关系（判断是否包含祖先）。
    - 如果通过，接收对方的 **表 B** 数据，并回放变更更新 **表 A**。

### 4. 如果不想用 SQL 怎么办？

如果写 SQL 麻烦，想要更极致的“JSON 化”，可以使用 **LiteDB** (C#/.NET) 或 **LowDB** (Node.js)。

- **LiteDB**：就是一个单文件的 NoSQL 数据库，直接存 JSON 文档，支持索引。非常适合你的 `ISyncable` 接口。
- **LowDB**：直接把整个数据库存成一个 `db.json` 文件。
    - *缺点*：并发写入性能差（因为是锁文件），但在单机 P2P 场景下完全够用。

### 总结

需要数据库。

- **最推荐**：**SQLite**。因为它既存 JSON（最新数据），又存关系（DAG 历史），且单文件、极轻量、性能强悍。
- **核心原则**：**“对象表”存业务，“提交表”存历史。** 不要混在一起。


## 实现：代码框架

假如现在有一个成熟chrome extension项目，没有同步功能，现在我们新增同步模块 jsonGitLite，列一个文件组织形式,看看应该如何组织这个同步模块的源代码和配置等。

这是一个非常棒的实战场景！将 `JsonGitLite` 作为一个**独立模块**植入到现有的 Chrome 插件中，我们需要遵循**“高内聚，低耦合”**的原则。

同步模块应该像一个“黑盒”：现有的业务代码只需要调用 `save()` 和 `sync()`，而不需要关心背后的 DAG 和 P2P 细节。

基于 Chrome 插件 **Manifest V3** 的架构（Service Worker + Content Scripts + Popup），我为你设计了以下的文件组织形式：

### 🧩 核心文件职责详解

#### 1. `json-git-lite/models/interfaces.ts`
**职责**：定义“契约”。你的原有业务对象（比如 `Note` 或 `Bookmark`）必须实现这里的 `ISyncable` 接口，才能被引擎接纳。

```typescript
// 核心接口：任何想被同步的数据都必须实现这个
export interface ISyncable {
  id: string;
  type: string;
  version: number;
  deleted: boolean;
  // 用于计算哈希的标准化数据
  getHashInput(): string; 
  // 合并逻辑（如果业务层不实现，引擎可用默认策略）
  merge(remote: ISyncable): MergeResult; 
}
```

#### 2. `json-git-lite/storage/Database.ts`
**职责**：封装底层存储。
*   **建议**：在 Chrome 插件中，由于 Service Worker 的生命周期限制，推荐使用 **IndexedDB**（通过 `idb` 库封装）或者 **SQLite WASM**（如果你追求极致性能且能接受加载时间）。
*   **功能**：提供 `saveObject()`, `getCommit()`, `getHead()` 等原子操作。

#### 3. `json-git-lite/network/Protocol.ts`
**职责**：定义 P2P 握手的消息格式，确保类型安全。

```typescript
// 定义握手消息
export interface HandshakeReq {
  head: string; // 本地 HEAD hash
}
export interface PushCheckReq {
  hash: string;
  parents: string[];
}
// ...其他协议结构
```

#### 4. `json-git-lite/engine/SyncEngine.ts`
**职责**：大脑。
*   它持有 `Database` 实例和 `Peer` 实例。
*   它提供两个核心方法给外部调用：
    1.  `commitChange(obj: ISyncable)`: 业务层数据变了，调用这个生成 Commit。
    2.  `syncWith(url: string)`: 用户点击同步按钮，调用这个开始 P2P 握手。

### 🔗 如何与原有业务集成？

假设你原来有一个“笔记”功能，集成步骤如下：

#### 第一步：改造业务对象
让你的 `Note` 类实现 `ISyncable`。

```typescript
// app/models/Note.ts
import { ISyncable } from '../../json-git-lite/models/interfaces';

export class Note implements ISyncable {
  id: string;
  type = 'Note';
  title: string;
  content: string;
  version: number = 1;
  deleted: boolean = false;

  // 实现接口方法
  getHashInput(): string {
    // 只序列化核心数据，排除元数据
    return JSON.stringify({ id: this.id, title: this.title, content: this.content, version: this.version });
  }
  
  merge(remote: ISyncable): MergeResult {
     // 简单的字段级合并逻辑，或者抛给引擎处理
     return { status: 'CONFLICT', local: this, remote: remote };
  }
}
```

#### 第二步：在 Service Worker 中初始化引擎
在 `background.js` (或 `background.ts`) 中初始化单例。

```typescript
import { SyncEngine } from './json-git-lite/engine/SyncEngine';
import { Database } from './json-git-lite/storage/Database';

// 初始化单例
const db = new Database();
const syncEngine = new SyncEngine(db);

// 监听来自 Popup 的同步请求
chrome.runtime.onMessage.addListener((msg, sender, sendResponse) => {
  if (msg.type === 'TRIGGER_SYNC') {
    syncEngine.syncWith(msg.peerUrl).then(() => {
      sendResponse({ status: 'success' });
    });
  }
});
```

#### 第三步：在 UI 中调用
在 `popup` 页面中，当用户点击“同步”按钮时：

```javascript
// 发送消息给后台
chrome.runtime.sendMessage({ type: 'TRIGGER_SYNC', peerUrl: 'ws://192.168.1.5:8080' });
```

### 💡 关键注意事项

1.  **权限配置 (`manifest.json`)**：
    *   你需要申请 `"storage"` 权限（用于存数据）。
    *   你需要申请 `"websocket"` 或 `"host_permissions"`（用于 P2P 连接，例如 `"<all_urls>"` 或具体的 IP 段）。

2.  **Service Worker 保活**：
    *   Chrome MV3 的后台是临时的。如果同步正在进行中（P2P 连接中），浏览器可能会杀掉后台。
    *   **解决方案**：在 `SyncEngine` 中保持一个 `keep-alive` 的定时器，或者使用 `chrome.alarms` 来确保同步任务不被意外中断。

3.  **UI 反馈**：
    *   同步是异步的。你需要在 `json-git-lite/utils/EventBus.ts` 中实现一个事件总线。
    *   当 `ConflictResolver` 发现冲突时，发出 `CONFLICT_DETECTED` 事件。
    *   `popup` 页面监听这个事件，弹出界面让用户进行“手动合并”。

这样组织，你的同步模块既独立又强大，完全符合“JsonGitLite”的设计理念！
