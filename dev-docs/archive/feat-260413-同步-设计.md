## 设计

### 📦 核心数据模型：一切皆对象

没有“文件”和“文件夹”，只有**集合**和**对象**。

把git中传统的文件管理 迁移为 

#### 1. 数据对象
每个业务数据（如一条笔记、一个任务）都是一个标准的 JSON 对象。为了实现通用同步，它必须包含以下**保留字段**：

```json
{
  "id": "obj_note_001",        // [必填] 全局唯一 ID (主键)
  "type": "note",               // [必填] 类型标识 (用于区分业务)
  "version": 1,                 // [必填] 版本号 (每次修改 +1)
  "data": {                     // [业务数据] 实际内容
    "title": "我的设计思路",
    "content": "..."
  },
  "deleted": false              // [必填] 软删除标记 (true 代表删除)
}
```

#### 2. 提交对象
这是模仿 Git 的 Commit，但它记录的是**对象集合的快照**或**增量**。为了轻量，我们采用**“引用 + 增量”**模式。

```json
{
  "hash": "a1b2c3...",          // 自身哈希 (SHA-256)
  "parents": ["d4e5f6..."],     // 父节点哈希 (DAG 的核心，可以是1个或2个)
  "timestamp": 1678888888,      // 时间戳
  "changes": [                  // 变更集 (Delta)
    {
      "targetId": "obj_note_001",
      "action": "UPDATE",        // CREATE | UPDATE | DELETE
      "content": { ... }         // 完整的 JSON 对象 (为了简单，不传部分更新)
    }
  ]
}
```
#### 3. 创世 Hash（Genesis Hash）
DAG 的公共起点，所有设备共享同一个常量值：

```
GENESIS_HASH = '0000...0000'  // 64个0
```

- 是一个**虚节点**，不实际写入数据库
- 新安装插件时，本地 HEAD 初始化为 `GENESIS_HASH`
- `DAGManager.hasAncestor` 和 `findLCA` 遇到它直接返回，无需查表
- 握手时两端均以真实 hash 或 `GENESIS_HASH` 表示自身 HEAD，协议无需特判 null

| 本地 HEAD | 远端 HEAD | 结果 |
|---|---|---|
| GENESIS_HASH | GENESIS_HASH | 双方都是新装，无需同步 |
| GENESIS_HASH | abc123 | 本地无历史，全量拉取远端所有 commits |
| abc123 | GENESIS_HASH | 远端是新装，直接 push 即可（远端 fast-forward） |
| abc123 | def456 | 正常流程，找 LCA 算差异 |
---

说明：`HEAD` 字段永远不可为 null，使用 `GENESIS_HASH` 来表示空历史；



### 🔄 同步协议流程 (P2P 握手)

下面给出一个清晰、可实现的分步流程，参考 Git 的 fetch/push 思路（握手 → 协商缺失 → 传输 → 合并 → 推送检查 → 推送）。消息名为示例，可按实现细化。

1. 建立连接（Connect）
    - 双方建立可靠通道（WebSocket 或类似），并准备进入握手流程。

2. 握手（HANDSHAKE_REQ / HANDSHAKE_RESP）
    - A 发送 `HANDSHAKE_REQ { head: A_HEAD, recent: [A_RECENT_HASHES?] }`。
    - B 返回 `HANDSHAKE_RESP { head: B_HEAD, wantInfo: boolean }`。
    - 目的：快速交换双方当前 HEAD，决定是否需要进一步协商缺失的 commits 或直接进入拉取/推送步骤。

3. 协商缺失（可选的 HAVE/WANT 轮次，用于减少 RTT 与带宽）
    - 若历史差异明显或提交数量较多，采用多轮协商：
      - A 发送 `HAVE { hashes: [h1,h2,...] }`（从最新往历史列出若干 hash）。
      - B 检查这些 hash，返回 `WANT { missing: [hash_oldest,...,hash_newest] }`，表示 B 需要哪些提交。
    - 或者简单方式：B 在 `HANDSHAKE_RESP` 直接返回 `missingCommits: [oldest...newest]`。
    - 结果：确定一侧需要被传输的 commits 列表（按从旧到新顺序）。

4. 拉取/传输提交（PULL_REQ / PULL_RESP 或 PUSH_DATA）
    - 请求方按缺失列表逐批请求提交：`PULL_REQ { commitHash }` → `PULL_RESP { commit }`。
    - 为效率可批量或使用打包（pack）格式：`PULL_REQ { commits: [h1,h2... ] }` → `PULL_RESP { commits: [...] }`。
    - 接收方将收到的 commit 存入临时区（temp area），并保证幂等（通过 hash 去重）。

5. 本地应用与合并（apply + merge）
    - 将拉取到的 commit 按拓扑（从旧到新）回放到本地 DAG，并对每个变更调用 `ISyncable.merge()`。
    - 若出现冲突，记录到 `ConflictResolver.pendingConflicts`，返回状态 `NEEDS_MERGE` 并暂停自动推送；等待用户解决后再继续。
    - 若无冲突，本地 HEAD 前进到最新 commit（fast-forward 或自动合并产生的新 merge commit）。

6. 推送预检（PUSH_CHECK / PUSH_CHECK_RESP）
    - 当 A 要把本地变更推送到 B 时，先发送 `PUSH_CHECK { candidate: commit }`，其中 `candidate.parents` 包含 A 与 B 的父引用（例如 [A_OLD_HEAD, B_HEAD] 或仅候选 commit 的 parents）。
    - B 使用 `DAGManager.hasAncestor(candidate.hash, B_HEAD)` 或通过检查 parents 是否包含 B_HEAD 来判断是否允许 fast-forward。
    - 返回 `PUSH_CHECK_RESP { allowed: true }` 或 `{ allowed: false, reason: 'NEED_PULL', remoteHead: B_HEAD }`。

7. 推送数据（PUSH_DATA / PUSH_ACK）
    - 若预检通过，A 发送 `PUSH_DATA { commits: [...] }`（仅发送 B 缺失的 commits，按旧→新顺序）。
    - B 应按顺序校验并写入 `commits` 表，最后更新 refs（atomic：先写 commits，再更新 refs 指向新 hash）。
    - B 返回 `PUSH_ACK { status: 'OK' }`，或在失败时返回具体错误（如冲突、验证失败）。

8. 异常与回退策略
    - 若 `PUSH_CHECK` 被拒（NEED_PULL），A 应执行一次 `pull`（按上面拉取流程），解决冲突或合并后重新尝试 `push`（推荐使用 `--force-with-lease` 风格的谨慎操作由用户确认）。
    - 对于大批量传输，优先使用打包与增量确认（分块传输 + 校验点），以便在 Service Worker 被回收时可续传。

消息示例与注意点：
    - 所有提交由哈希唯一标识，传输时可仅发送 `hash`+`parents` 做快速校验，必要时再请求 `changes`（节省带宽）。
    - 推荐按旧→新顺序传输 commits，便于一次性回放并保持事务性更新 refs。
    - 对于离线或无历史互通的场景，`GENESIS_HASH` 用于表示空历史，握手逻辑应能正确处理该虚点。

该流程与 `feat-260413-git的pull和push.md` 中的 pull/push 思路一致，实际实现时可把 `HANDSHAKE`、`HAVE/WANT`、`PULL`、`PUSH_CHECK`、`PUSH_DATA` 等消息抽象为 `Peer` 类方法并加入打包/断点续传支持。

## 设计：细节补充： push 握手

在p2p握手的第4步，A发送的完整内容应该是什么样的，才能方便让B检查包含关系，从而决定是否允许推送？

### 📨 推送预检请求结构

A 只需要发送**“合并提交的完整对象”**即可。因为合并提交中包含了父节点指针，B 可以通过递归回溯来判断包含关系。

#### 发送内容示例

A 向 B 发送一个 `PUSH_CHECK` 消息，核心载荷是**新生成的合并 Commit 对象**：

```json
{
  "action": "PUSH_CHECK",
  "payload": {
    "hash": "abc123...",       // 新合并提交的哈希
    "parents": [
      "local_head_hash",       // A 的原 HEAD
      "remote_head_hash"       // B 的 HEAD (关键！B 会检查这个)
    ],
    "timestamp": 1678888888,
    "changes": [...]            // 变更集（可选，仅用于预校验数据完整性）
  }
}
```

#### B 的检查逻辑
B 收到后，只需执行一步简单的逻辑判断：

1.  **提取父节点**：读取 `payload.parents` 列表。
2.  **包含性验证**：
    - 检查 `remote_head_hash`（即 B 当前的 HEAD）是否存在于 `parents` 列表中。
    - 或者更严谨一点：检查 `remote_head_hash` 是否是 `payload.hash` 的**祖先节点**（通过递归读取父节点的父节点...）。
3.  **决策**：
    - **是**：说明 A 已经包含了 B 的最新历史，**允许推送**。
    - **否**：说明 A 是基于旧版本提交的，**拒绝推送**。

> **提示**：为了节省带宽，如果 Commit 对象很大，A 也可以只发送 `hash` 和 `parents` 字段，B 若通过校验，再请求完整的 `changes` 数据。

### 🛠️ 通用同步层设计

为了实现“通用”，我们将同步逻辑与业务数据解耦。

#### 接口定义
你的代码库中只需要实现一个简单的接口，任何业务对象只要实现它，就能被同步：

```typescript
interface ISyncable {
  id: string;
  version: number;
  // 序列化：用于计算哈希和传输
  toJSON(): string; 
  // 合并：核心冲突处理逻辑
  merge(other: ISyncable): ISyncable; 
}
```

// 示例：`Bookmark` 的 ISyncable 参考实现（供前端直接复用）
```javascript
function createBookmark({ id, url, title, tags = [] }) {
    return {
        id,
        type: 'Bookmark',
        version: 1,
        deleted: false,
        url,
        title,
        tags,

        getHashInput() {
            return JSON.stringify({ id: this.id, url: this.url, title: this.title, tags: this.tags });
        },

        merge(remote) {
            const conflicts = [];
            const resolved = { ...this };
            if (remote.url !== this.url) conflicts.push('url');
            if (remote.title !== this.title) conflicts.push('title');
            resolved.tags = Array.from(new Set([...(this.tags || []), ...(remote.tags || [])]));
            if (conflicts.length) return { status: 'CONFLICT', local: this, remote };
            resolved.version = Math.max(this.version || 0, remote.version || 0) + 1;
            return { status: 'SUCCESS', resolved };
        }
    };
}
```

#### 同步管理器
这是一个单例类，负责管理 P2P 连接和 DAG 图，它不关心数据是什么，只管 `ISyncable`。

*   `pull(peerUrl)`: 从远端拉取缺失的 commits，执行本地合并（可能触发冲突挂起）。
*   `push(peerUrl)`: 推送本地领先的 commits 到远端（充要条件：远端 HEAD 是本地 HEAD 的祖先，远端执行 fast-forward）。
*   `sync(peerUrl)`: `pull` → 等冲突解决 → `push` 的组合，常见的一键同步入口。
*   `getConflicts()`: 获取当前需要手动处理的冲突列表。
*   `resolveConflict(id, strategy)`: 用户解决冲突后调用，完成后自动触发 `push`。

## 设计：类和方法，流程

基于你确定的**“JsonGit-Lite”**协议（P2P、JSON对象、DAG、手动合并、无身份验证），我为你梳理了核心代码结构。这套设计采用了**“依赖倒置”**原则，将通用的同步引擎与具体的业务数据剥离。

以下是核心类与接口的初稿设计：

---

### 🧱 核心接口与数据结构

这部分定义了“什么可以被同步”以及“数据长什么样”。

#### 1. `ISyncable` (接口)
**职责**：定义所有需要同步的业务对象的通用行为。任何实现了此接口的类（如 `Note`, `User`, `Task`）都能被同步引擎自动管理。

**核心方法**：
- `getId(): string`
    - **职责**：返回对象的全局唯一标识符。
- `getVersion(): number`
    - **职责**：返回当前对象的版本号（用于冲突检测）。
- `getHashInput(): string`
    - **职责**：返回用于计算哈希的标准化字符串（通常是去除了元数据的 JSON 序列化字符串）。
- `merge(remote: ISyncable): MergeResult`
    - **职责**：**核心逻辑**。对比 `this`（本地）和 `remote`（远程）的数据。
    - **返回**：
        - 若无冲突，自动合并并返回 `SUCCESS`。
        - 若有冲突，返回 `CONFLICT`，并保留双方数据供后续处理。

#### 2. `Commit` (类/结构)
**职责**：对应 Git 中的 Commit 对象，是 DAG 的节点。它不存储业务数据本身，而是存储对数据的“变更操作”。

**核心字段**：
- `hash: string`：自身的 SHA-256 哈希值。
- `parents: string[]`：父节点哈希列表（1个代表普通提交，2个代表合并提交）。
- `timestamp: number`：创建时间戳。
- `authorId: string`：创建者的设备 ID。
- `changes: Change[]`：变更集列表。

#### 3. `Change` (类/结构)
**职责**：描述一次具体的修改动作。

**核心字段**：
- `targetId: string`：被修改的业务对象 ID。
- `type: string`：对象类型（如 "Note"）。
- `action: 'CREATE' | 'UPDATE' | 'DELETE'`：操作类型。
- `payload: object`：完整的 JSON 对象数据（为了轻量，直接存全量快照）。

---

### ⚙️ 同步引擎核心

这部分是“通用逻辑”，不关心业务，只负责搬运和校验数据。

#### 4. `SyncEngine` (类)
**职责**：同步流程的控制器，负责协调存储、网络和数据合并。

**核心字段**：
- `store: IObjectStore`：本地数据存储接口。
- `dag: DAGManager`：DAG 图管理器。
- `conflictResolver: ConflictResolver`：冲突处理管理器。

**核心方法**：
- `async connect(peerUrl: string): Promise<void>`
    - **职责**：建立与远程 Peer 的网络连接（WebSocket/TCP）。
- `async sync(peer: Peer): Promise<SyncStatus>`
    - **职责**：执行完整的同步流程（握手 -> 拉取 -> 合并 -> 推送）。
- `private async pullChanges(peer: Peer): Promise<Commit[]>`
    - **职责**：
        1. 发送本地 HEAD。
        2. 接收远程缺失的 Commit 列表。
        3. 将 Commit 存入本地临时区。
- `private async pushChanges(peer: Peer): Promise<boolean>`
    - **职责**：
        1. 执行**推送预检**（发送拟推送的 Commit，检查是否包含远程 HEAD）。
        2. 若预检通过，传输数据。
- `private async applyCommits(commits: Commit[]): Promise<void>`
    - **职责**：将拉取下来的 Commit 应用到本地数据库，并触发对象合并逻辑。

#### 5. `DAGManager` (类)
**职责**：管理提交历史图，计算哈希和祖先关系。

**核心方法**：
- `createCommit(parents: string[], changes: Change[]): Commit`
    - **职责**：构建一个新的 Commit 对象，并计算其哈希。
- `hasAncestor(commitHash: string, ancestorHash: string): boolean`
    - **职责**：**关键校验**。判断 `ancestorHash` 是否是 `commitHash` 的祖先（用于推送预检）。
- `findLCA(hashA: string, hashB: string): string`
    - **职责**：寻找两个提交的最近公共祖先，用于计算差异。

---

### 🛠️ 冲突与存储

#### 6. `ConflictResolver` (类)
**职责**：处理 `ISyncable.merge` 返回的冲突，管理“手动合并”的生命周期。

**核心字段**：
- `pendingConflicts: ConflictItem[]`：当前挂起的冲突列表。

**核心方法**：
- `addConflict(local: ISyncable, remote: ISyncable): string`
    - **职责**：记录冲突，生成一个冲突任务 ID，并暂停同步流程。
- `resolve(conflictId: string, strategy: 'LOCAL' | 'REMOTE' | 'MANUAL', data?: object): void`
    - **职责**：
        - 用户选择策略后，生成最终的对象数据。
        - 创建一个新的“合并 Commit”来固化这个结果。
        - 从 `pendingConflicts` 中移除该任务。        
        - **自动触发 `push`**，恢复同步流程的续传，无需用户再次操作。
        
#### 7. `ObjectStore` (类/接口)
**职责**：底层的 CRUD 操作，类似于 Git 的对象数据库。

**核心方法**：
- `get(id: string): ISyncable`
- `save(obj: ISyncable): void`
- `getAllIds(): string[]`
    - **职责**：用于握手阶段生成“本地已知 ID 列表”。

---

### 📝 交互流程简述（代码视角）

1. **用户修改数据** -> 调用 `store.save(note)` -> 引擎自动生成 `Commit` (Parent: 本地HEAD)。
2. **用户点击同步** -> `engine.sync(peer)`。
3. **引擎** -> `pullChanges` -> 发现远程有新数据 -> 拉取。
4. **引擎** -> `applyCommits` -> 发现 `note` 冲突 -> `conflictResolver.addConflict`。
5. **引擎** -> 暂停，返回状态 `NEEDS_MERGE`。
6. **UI层** -> 显示冲突 -> 用户手动修改 -> 调用 `resolver.resolve`。
7. **引擎** -> 生成 `Merge Commit` (Parents: [本地, 远程]) -> `pushChanges`。
8. **引擎** -> 发送 `PUSH_CHECK` -> 远程验证 `hasAncestor` -> 通过 -> 推送成功。

这套结构非常干净，**`SyncEngine` 完全不知道 `Note` 是什么，它只知道 `ISyncable`**，完美符合你的“通用复用”需求。

## 设计：存储

没错，确实得存起来。不过咱们这个场景比较特殊，因为你要模仿 Git 的核心机制，所以这个“数据库”不能只是简单地往里扔 JSON 就完事了。

普通的数据库（比如 MySQL 或 MongoDB）通常只管“最新状态”，而你的设计需要同时管理**“最新状态”**和**“历史记录（DAG）”**。

为了保持你追求的“轻量级”和“Git 特性”，我建议采用**“混合存储模式”**。具体来说，你需要存两份东西：

### 1. 为什么要存两份？

- **工作区**：你需要快速读取当前的 JSON 对象（比如打开笔记列表），不能每次都去遍历 DAG 历史反算，太慢了。
- **版本库**：你需要存储 Commit 和 DAG 结构，用于同步、冲突检测和版本回溯。

### 2. 推荐的存储方案：SQLite（单文件）

既然是 P2P 且轻量，**SQLite** 是目前的最佳选择。它是一个单文件的嵌入式数据库，不需要单独部署服务器，非常适合你的架构。

#### 数据库表结构设计 (Schema)

你只需要三张核心表，就能完美支撑你的协议：

**表 A：对象表 —— 存“当前状态”**
*这是你的“工作区”，对应 Git 的 Working Directory。*

| 字段名 | 类型 | 说明 |
| :--- | :--- | :--- |
| **id** | TEXT (PK) | 业务对象 ID (如 `note_001`) |
| **type** | TEXT | 类型 (如 `Note`) |
| **content** | BLOB/TEXT | **完整的 JSON 数据** |
| **version** | INT | 当前版本号 |
| **updated_at** | INT | 最后更新时间 |

**表 B：提交表 —— 存“DAG 结构”**
*这是你的“版本库”，对应 Git 的 .git 目录。*

| 字段名 | 类型 | 说明 |
| :--- | :--- | :--- |
| **hash** | TEXT (PK) | Commit 的哈希值 |
| **parents** | TEXT | 父节点哈希列表 (JSON 数组存储) |
| **timestamp** | INT | 时间戳 |
| **changes** | BLOB | 变更集 (包含具体的 JSON 变更数据) |

**表 C：引用表 —— 存“指针”**
*对应 Git 的 refs/heads/master。*

| 字段名 | 类型 | 说明 |
| :--- | :--- | :--- |
| **name** | TEXT (PK) | 分支名 (如 `main`) |
| **target_hash** | TEXT | 指向 `提交表` 的 hash |

### 3. 数据流转逻辑

当你执行操作时，数据是这样流动的：

1. **用户修改笔记**：
    - 更新 **表 A (对象表)**。
    - *此时数据库里只有最新数据，还没生成历史。*

2. **用户提交 (Commit)**：
    - 引擎读取 **表 A** 的变化。
    - 生成一个新的记录插入 **表 B (提交表)**。
    - 更新 **表 C (引用表)** 指向新 Hash。

3. **同步 (Sync)**：
    - 对方发来 `PUSH_CHECK`。
    - 你查询 **表 B** 和 **表 C** 来计算 DAG 关系（判断是否包含祖先）。
    - 如果通过，接收对方的 **表 B** 数据，并回放变更更新 **表 A**。

### IndexedDB (Browser / Chrome MV3) 备选方案

在 Chrome 扩展里更常用的是 `IndexedDB` 而非 SQLite（后者需要 WASM）。下面给出一个可直接用于实现的 `IndexedDB` schema 建议，便于把设计落地到 `Service Worker` 中：

- `objectStore: objects`
    - keyPath: `id`
    - value: `{ id, type, content, version, updated_at }`
- `objectStore: commits`
    - keyPath: `hash`
    - value: `{ hash, parents: string[], timestamp, changes }`
    - index: `byTimestamp`
- `objectStore: refs`
    - keyPath: `name`
    - value: `{ name, target_hash }`
- `objectStore: conflicts`
    - keyPath: `id`
    - value: `{ id, local, remote, created_at }`

初始化策略：在 `onupgradeneeded` 中创建上述 objectStore，并为 `commits` 建立 `byTimestamp` 索引以便 GC 和回放。首次打开数据库时，确保 `refs.main` 指向 `GENESIS_HASH`。

迁移考虑：如果未来从 SQLite/WASM 切换或从旧 schema 升级，建议在 `version` 增量中编写清晰的迁移步骤（复制、转换、swap），并在迁移期间暂停同步任务。

### Service Worker 保活与重试（设计级指导）

Chrome MV3 的后台是短生命周期的 Service Worker，网络连接容易被中断。设计时应考虑：

- 使用 `chrome.alarms` 做周期性唤醒（如每 5 分钟），在唤醒时检测未完成的同步任务并恢复。
- 在长连接场景下（例如 WebSocket），在连接断开时记录断线时间并启动指数退避重连（base=1s, factor=2, max=60s）。
- 在进行长操作（拉取大量 commits）时分段执行：每次拉取 50-200 个 commit 并 commit 到 IndexedDB，然后释放事件循环，降低 SW 被回收的风险。
- 错误分类：
    - 致命错误（权限缺失、认证失败）——停止并上报给 UI；
    - 临时网络错误——按照指数退避自动重试；
    - 逻辑错误（push 被拒绝）——建议自动触发 `pull`，若仍冲突则交给用户解决。

### 错误处理与重试（详版）

分类：
- 临时网络错误（可重试）
- 逻辑拒绝（如 `NEED_PULL`、版本冲突）
- 存储失败（磁盘配额、事务失败）
- 永久错误（认证失败、参数校验失败）

策略要点：
- 对所有可重试错误采用指数退避 + 随机抖动（jitter），并限定最大尝试次数与最大延迟。
- 将重试任务持久化到 `retryQueue`（IndexedDB），并使用 `chrome.alarms` 驱动执行，保证 SW 重启后仍可恢复。
- 对 `push` 被拒情形，自动执行有限次数的 `pull`，在无法自动解决时上报用户介入。

推荐默认参数：`base=1000ms, factor=2, maxDelay=60000ms, maxAttempts=8, jitter=0.5`。

全局重试包装器（伪代码）同 `实现文档` 中所示，Service Worker 的 `chrome.alarms` 处理循环应从 `retryQueue` 中取出即将到期的任务并用包装器执行。

长拉取策略：分块（batch）拉取并在 `syncProgress` 中持久化每批完成的位置，允许断点续传。

关于幂等性：
- 所有 commit 用哈希唯一标识，重试时仅发送未被对端确认的 commit；请求可带 `requestId` 用于对端去重。

用户提示与监控：
- 连续失败超过阈值时，触发 `PEER_UNREACHABLE` 事件并在 UI 显示重试建议或允许用户禁用某个 peer 的自动重试。


### SyncEngine（设计级伪代码）

以下伪代码用于统一设计与实现预期：

function pull(peerUrl) {
    connect(peerUrl)
    send({ action: 'HANDSHAKE_REQ', body: { head: localHead } })
    const resp = await recv()
    for (const hash of resp.missingCommits) {
        send({ action: 'PULL_REQ', body: { commitHash: hash } })
        const commit = await recv()
        storeTemp(commit)
    }
    const conflicts = applyCommitsFromTemp()
    if (conflicts.length) emit('CONFLICT_DETECTED', conflicts)
    return { status: conflicts.length ? 'NEEDS_MERGE' : 'OK' }
}

async function push(peerUrl) {
    connect(peerUrl)
    const candidate = localHead
    send({ action: 'PUSH_CHECK_REQ', body: { hash: candidate.hash, parents: candidate.parents } })
    const ok = await recv()
    if (!ok.allowed) return { status: 'NEED_PULL', reason: ok.reason }
    const commits = collectCommitsMissingOnPeer()
    send({ action: 'PUSH_DATA', body: { commits } })
    return { status: 'OK' }
}

async function sync(peerUrl) {
    const pullResult = await pull(peerUrl)
    if (pullResult.status === 'NEEDS_MERGE') return pullResult
    return await push(peerUrl)
}

注：真实实现应把 `connect()`、`send()`、`recv()` 抽象到 `Peer` 类，并处理消息幂等、时间戳与错误。
// 冲突 UI 示例（在 popup 中的最小实现）

当 `pull()` 发现冲突时，`SyncEngine` 会发出 `EventBus.emit('CONFLICT_DETECTED', { conflictId, local, remote })`。
前端（`popup`）可以监听并呈现如下最小交互：

```html
<div id="conflict-list"></div>
<script>
    EventBus.on('CONFLICT_DETECTED', ({ conflictId, local, remote }) => {
        const root = document.getElementById('conflict-list');
        const el = document.createElement('div');
        el.innerHTML = `\
            <div class="conflict" data-id="${conflictId}">\
                <h4>Conflict: ${conflictId}</h4>\
                <pre class="local">${JSON.stringify(local, null, 2)}</pre>\
                <pre class="remote">${JSON.stringify(remote, null, 2)}</pre>\
                <button class="btn-local">Use Local</button>\
                <button class="btn-remote">Use Remote</button>\
                <button class="btn-manual">Manual Edit</button>\
            </div>`;
        root.appendChild(el);

        el.querySelector('.btn-local').onclick = () => {
            chrome.runtime.sendMessage({ type: 'RESOLVE_CONFLICT', conflictId, strategy: 'LOCAL' });
        };
        el.querySelector('.btn-remote').onclick = () => {
            chrome.runtime.sendMessage({ type: 'RESOLVE_CONFLICT', conflictId, strategy: 'REMOTE' });
        };
        el.querySelector('.btn-manual').onclick = () => openManualEditor(conflictId, local, remote);
    });
</script>
```

Service Worker 收到 `RESOLVE_CONFLICT` 后应调用 `ConflictResolver.resolve(conflictId, strategy, data)`，随后自动尝试 `push()`。

消息结构（示例）:

```json
{
    "type": "RESOLVE_CONFLICT",
    "conflictId": "<id>",
    "strategy": "LOCAL|REMOTE|MANUAL",
    "data": { /* optional: manual merged object */ },
    "peerUrl": "ws://..." // optional, 用于 resolve 后直接续传
}
```

Service Worker 端示例处理（伪代码）：

```javascript
chrome.runtime.onMessage.addListener((msg, sender, sendResponse) => {
    if (msg.type === 'RESOLVE_CONFLICT') {
        const { conflictId, strategy, data, peerUrl } = msg;
        ConflictResolver.resolve(conflictId, strategy, data)
            .then(() => peerUrl ? SyncEngine.push(peerUrl) : Promise.resolve())
            .then(() => sendResponse({ status: 'ok' }))
            .catch(err => sendResponse({ status: 'error', message: err.message }));
        return true; // async
    }
});
```

### 4. 如果不想用 SQL 怎么办？

如果写 SQL 麻烦，想要更极致的“JSON 化”，可以使用 **LiteDB** (C#/.NET) 或 **LowDB** (Node.js)。

- **LiteDB**：就是一个单文件的 NoSQL 数据库，直接存 JSON 文档，支持索引。非常适合你的 `ISyncable` 接口。
- **LowDB**：直接把整个数据库存成一个 `db.json` 文件。
    - *缺点*：并发写入性能差（因为是锁文件），但在单机 P2P 场景下完全够用。

### 总结

需要数据库。

- **最推荐**：**SQLite**。因为它既存 JSON（最新数据），又存关系（DAG 历史），且单文件、极轻量、性能强悍。
- **核心原则**：**“对象表”存业务，“提交表”存历史。** 不要混在一起。
