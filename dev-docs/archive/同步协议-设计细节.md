# 同步协议 — 设计细节（伪代码级别）

说明：本文件把 `同步协议.md` 的思想细化为编程级别的设计说明，列出所有抽象实体、字段约定、哈希/序列化规则、服务器与客户端 API，以及关键伪代码流程，便于直接实现或用于编写单元测试。

## 目标回顾
- 适用于多设备（手机、电脑、平板）与一个在线同步服务器的场景。主要数据为短文本对象（单条 ~200 字符）。
- 要点：全局唯一 ID（UUID）、内容指纹（SHA-256）、操作日志（opLog）驱动同步、基于因果关系（parents）合并、客户端负责冲突解决。

---

## 术语与抽象实体

- `SyncInterface`（同步接口 / 抽象类）
  - 语义：同步协议约定的抽象接口或基类。不同业务对象应继承或实现该接口并提供自己的 `hash()` 方法。
  
  - 接口说明（伪代码）：
    class SyncInterface {
        // 子类必须实现：返回对象的全局 ID（字符串），例如 UUID
        id() { throw new Error('override id() in subclass') }
        
        // 子类必须实现：返回与文档中一致的 content 指纹（hex sha256）
        // 注意：基类不定义构造器或字段，具体业务类自行定义自己的字段和构造器。
        hash() { throw new Error('override hash() in subclass') }
    }

  - 实例（由具体业务类生成）示例：
    {
      "id": "uuid-...",           // 全局不变 ID
      "content": { ... },          // 业务字段（任意 JSON 对象）
      "last_device_id": "dev-1", // 可选，非内容域
      "hash": "..."              // 由具体实现计算并填充
    }
  
  - 说明：文档其余部分中所称的 "SyncObject" 指的是实现了 `SyncInterface` 的业务对象实例（通常由业务类提供 `hash()` 实
  现）。

- `Change`（单条变更）
  - 结构：
    {
      "target_id": "uuid-...",
      "action": "new|update|delete",
      // 当 action != delete：
      "data": { ... },    // 新的对象内容（业务 JSON）
      "hash": "..."      // data 的内容哈希
    }

Change.data 必须是对象的完整内容快照，绝不允许存增量描述（patch/diff）。同步层的 apply 逻辑是：用 data 整体覆盖本地对象，而非 merge。

- `Op` / `OpLog`（操作日志条目）
  - 结构（最小）：
    {
      "op_id": "sha256...",     // 本 op 的哈希 ID
      "device_id": "dev-...",
      "parents": ["op_id", ...],
      "timestamp": "ISO8601",
      "changes": [Change, ...]
    }

说明（批量与原子性，简要）：

- `Op` 是传输与事务的容器，可包含 1..N 个 `Change`，以表达一次网络/用户操作对多个对象的批量变更。

- 建议服务器以整个 `Op` 为原子单位：要么 `accept` 整个 `Op`，要么 `reject` 整个 `Op` 并返回拒绝原因（例如冲突或缺失 parents）。

- 为控制复杂度与资源占用，建议在协议中规定单个 `Op` 的上限（例如最多 100 个 `Change` 或总字节大小限制），客户端在被拒绝时可按该上限拆分重试。

- 若需要更细粒度接收（部分接受/部分拒绝），则需在 API 响应中明确返回 per-change 的接收状态与重试建议；此方案会增加服务器/客户端复杂度。


一般情况：多数应用确实会以「一个 Op 含一个 Change」为常态，但并非必须 —— 两种做法各有权衡。

要点（简短）：

单 change/op（简单模式）：实现最直观，易于回放、冲突判断、幂等；网络与存储开销较大但逻辑简单，适合多数单对象操作场景。

多 change/op（批量模式）：把多条 Change 打包到一个 Op 可减少网络请求、提供原子提交（一次性应用一组变更），适合批量编辑或事务性操作，但会增加冲突处理与重试复杂度。

推荐实践：协议支持 1..N changes（允许批量），但默认/常用路径使用 single-change op；服务器以整个 Op 为原子单位处理，并在文档中规定单 op 的上限（例如 change 数或字节数）和客户端拆分/重试策略。

- `Device`：每端有唯一 `device_id`，设备可持有私钥（用于可选签名）。
- `RepoState`（服务器/库观）：维护一个或多个 `head`（当前最新 op_id 列表），以及 op 表和对象表。

## 序列化、哈希与一致性规则

这些规则必须在所有端一致实现，才能保证哈希相等与去重生效。

1. 稳定序列化（Stable serialization）
   - 所有参与哈希的 JSON 对象必须使用按键名排序的序列化（例如：递归按字典序排序键，然后生成无空白的 JSON 文本）。
   - 数组保持顺序；对象按键排序。
   - 空值与缺省字段要有明确约定：缺省字段应视为不存在而不是 null。

2. 对象指纹（content_hash）
   - 计算方法（建议）：
     content_hash = SHA256( id + '|' + StableStringify(content) )
   - 其中 `id` 是对象的 UUID（字符串），`content` 是业务 JSON 对象（不含 `last_device_id`、`hash` 字段）。

3. op_id 生成
   - 计算方法（建议）：
     op_id = SHA256( device_id + '|' + timestamp + '|' + join(parents, ',') + '|' + join(change_hashes, ',') )
   - `change_hashes` 是按 `changes` 顺序的每个 change 的 `hash`（对 delete，使用空字符串或固定占位）。

## 虚拟根（Genesis）建议

  - 建议在协议中定义一个保留的根节点常量 `GENESIS_OP_ID`（例如 64 个 `'0'` 的 hex 字符串或其他约定的固定值），用于将“无父”情况标准化处理。
  - 语义与规则：在内部算法与存储中，`parents: []` 与 `parents: [GENESIS_OP_ID]` 应被视为等价。实践中可在写入/验证/遍历前把空父列表规范化为 `[GENESIS_OP_ID]`。服务器无需为 `GENESIS_OP_ID` 存储对应的 op 记录；只需在逻辑上认可该保留值作为根。
  - 好处：统一祖先检查与头集维护、避免在代码中对空父数组做特殊分支、使并发的“首个 op”显式成为同一祖先的子代，便于推理与调试。
  - 实现注意事项：
    - 在生成 `op_id` 时使用规范化后的父列表（若为空则包含 `GENESIS_OP_ID`），以防不同实现对空父的处理不一致导致 id 不同。
    - 验证/回放路径需允许 `GENESIS_OP_ID` 作为缺省且不可追溯的父项（即不报错缺失父项）。
    - 文档与测试用例应明确说明此规范化行为，且跨语言实现需在测试中确认相同行为。


4. 签名（可选但推荐）
   - 如果需要防篡改与身份不可否认，`op` 可以附加 `signature` 字段：签名内容为 `op` 的序列化字节，签名由设备私钥生成（例如 Ed25519）。服务器验证设备公钥。

## JSON Schema 摘要（伪 schema）

- Change
  - target_id: string (uuid)
  - action: enum("new","update","delete")
  - data?: object
  - hash?: string (hex sha256)

- Op
  - op_id: string (hex sha256)
  - device_id: string
  - parents: array[string]
  - timestamp: string (ISO8601)
  - changes: array[Change]
  - signature?: string (base64)

---

## Server 存储模型（建议）

- 表：`ops`（主表）
  - op_id PK, device_id, timestamp, parents (array), changes(JSON), signature

- 表：`heads`
  - 单行或多行记录当前 head(s) op_id 列表（用于快速校验父版本）

**对象数据（业务 content）不在同步层存储**——对象的当前状态由应用层自己的业务存储负责维护（类比 Raft 的状态机）。同步层只存 op 日志；apply op 时由应用层回调写入自己的对象存储。

维护原则：插入 op 时若 parents 全部可被追溯，则 accept；否则 reject 并返回缺失 parents 列表给客户端。

## HTTP API 设计（参考）

说明：使用 HTTP+JSON 作为简单示例，实际可用 WebSocket/gRPC。所有请求应在 TLS 下进行。

1) POST /sync/handshake
   - 请求：
     { "device_id": "dev-1", "known_heads": ["opA","opB"] }
   - 响应：
     { "server_heads": ["opX","opY"], "missing_ops": [op11, op12, ...] }
   - 语义：客户端告诉服务器其本地 head；服务器返回当前服务器 heads 和从客户端已知 head 到服务器 head 之间需要下发的 op 列表或直接返回 op id 列表让客户端拉取。

2) POST /sync/pullOps
   - 请求： { "from_op": "opN", "to_op": "opM" } 或 { "since": [opIds] }
   - 响应： { "ops": [Op, ...] }

3) POST /sync/pushOps
   - 请求： { "ops": [Op, ...] }
   - 响应： { "accepted": [op_id,...], "rejected": [{op_id, reason, missing_parents?:[...]}, ...] }
   - 语义：服务器对每个 op 做：验证签名（若有）、验证 parents 存在且为当前接受基点；若成功写入 ops 表并更新 heads；若失败返回拒绝原因。

4) GET /sync/object/:id
   - 响应： SyncObject

5) POST /sync/ack (可选)
   - 用于客户端向服务器确认已收到并本地合并某些 op（便于服务器 GC 策略）。

## 客户端伪代码流程（主要路径）

1) 握手 + 增量拉取（pull）

Pseudocode:

client_handshake(device_id, local_heads):
    resp = POST('/sync/handshake', {device_id, known_heads: local_heads})
    if resp.missing_ops not empty:
        ops = POST('/sync/pullOps', { since: local_heads })
        for op in ops:
            applyOpLocally(op)
    // 本地与服务器对齐至 server_heads

applyOpLocally(op):
    if !verifyOp(op):
        reject (log)
    for change in op.changes:
        if change.action == 'new':
            storeObject(change.target_id, change.data, change.hash)
        elif change.action == 'update':
            // detect conflict: local object hash != change.hash && local_op not ancestor
            if localObjectExists(change.target_id) and localObjectHash(change.target_id) != change.hash:
                createConflictCopy(change.target_id, localCopy, change.data)
            else:
                storeObject(...)
        elif change.action == 'delete':
            deleteLocalObject(change.target_id)

2) 本地变更 -> 生成 Op -> 推送（push）

createAndPushOp(device_id, parent_op_ids, changes):
    op = createOp({ device_id, parents: parent_op_ids, changes })  // uses stable serialization + hashes
    resp = POST('/sync/pushOps', { ops: [op] })
    if op accepted: mark local as synced
    if op rejected because server head changed:
        // 自动重试流程
        client_handshake(device_id, local_heads)   // 拉取最新
        merge local modifications with pulled ops (user resolve conflicts if any)
        createAndPushOp(...) // retry with new parents

Notes:
- 客户端必须基于服务器最新 heads（或通过 handshake 确认）来生成 op 的 parents，否则服务器拒绝。
- 在压缩或批量场景，`changes` 可包含多条 Change；生成 op 时按顺序计算每个 change 的 hash。

## 服务器伪代码（核心）

on POST /sync/pushOps(ops):
    for op in ops in order:
        if not verifyOp(op):
            add to rejected (reason: invalid hash/signature)
            continue
        if any parent in op.parents missing in DB:
            add to rejected (reason: missing_parents)
            continue
        // accept
        insert op into ops table
        update heads: remove parents from head set, add op.op_id
        // 不在同步层存对象；由调用方（应用层）通过 applyOpLocally 回调更新自己的业务存储
        add to accepted
    return {accepted, rejected}

Notes:
- 接受 op 必须保证幂等性：如果 op_id 已存在则视为已接受（忽略重复）。

## 冲突策略与 UX 要点

- 冲突检测：当应用一个变更时，如果本地最新对象 hash 与变更中的 hash 不同且两者并非父子关系，即认为冲突。
- 冲突处理策略（建议）：
  - 不自动合并；保存双方版本为 `id (conflict-from-<device>)` 的副本，并在 UI 中提示用户处理。
  - 提供自动合并钩子（可选）：对文本字段可尝试三方合并策略并在结果中标注冲突片段。

---

## 批量、压缩与历史管理

- 批量提交：客户端可一次性发送包含多个 change 的 op；服务器按顺序写入并返回接收状态。
- 快照 / 压缩（GC）：长期保留完整 opLog 会占用空间，建议服务器支持定期生成快照（snapshot）：
  - Snapshot 内容为「截止某个 op_id 的业务对象状态」，由应用层序列化提供（同步层不持有对象数据）。
  - GC 可删除早期已经被 snapshot 覆盖且被所有活跃客户端 ack 的 op。

---

## 安全与鉴权

- 传输层使用 TLS。
- 身份鉴别：设备注册时生成 `device_id` 与公钥（或使用 OAuth token）；服务器保存公钥用于验证 `op.signature`。
- 防篡改：op 的 `op_id` 为哈希且可签名；服务器应验证签名（若启用）。

## 测试用例建议

- 跨平台哈希一致性测试：在不同实现（浏览器 JS、后端 Node/Python）上对同一对象运行 `StableStringify` + `SHA256` 比对结果。
- 并发推送测试：两个客户端基于相同 parent 同时推送不同 op，验证服务器接受第一个并拒绝第二个，第二客户端自动重试流程能成功最终合并。
- 幂等性测试：重复提交相同 op，服务器应忽略重复并返回已存在信息。
