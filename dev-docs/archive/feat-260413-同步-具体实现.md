
## 实现：代码框架

可以参考 ./同步-设计.md, 但是具体实现以此文旦稳准。

假如现在有一个成熟chrome extension项目，没有同步功能，现在我们新增同步模块 jsonGitLite，


将 `JsonGitLite` 作为一个**独立模块**植入到现有的 Chrome 插件中，我们需要遵循**“高内聚，低耦合”**的原则。

同步模块应该像一个“黑盒”：现有的业务代码只需要调用 `save()` 和 `sync()`，而不需要关心背后的 DAG 和 P2P 细节。

基于 Chrome 插件 **Manifest V3** 的架构（Service Worker + Content Scripts + Popup），我为你设计了以下的文件组织形式：

### 🧩 核心文件职责详解

#### 1. `json-git-lite/models/interfaces.js`
**职责**：定义"契约"。用 JSDoc 描述 `ISyncable` 的结构，业务对象只需按约定实现对应字段和方法即可。同时导出 `GENESIS_HASH` 常量供全局使用。

```javascript
/**
 * 创世 Hash：所有设备共享的固定常量，代表 DAG 的起点。
 * 是一个虚节点，不实际存入 DB；DAGManager 遇到它时直接视为公共祖先。
 * 首次安装插件时 HEAD 即指向此值。
 */
export const GENESIS_HASH = '0'.repeat(64);

/**
 * @typedef {Object} MergeResult
 * @property {'SUCCESS'|'CONFLICT'} status
 * @property {ISyncable} [resolved]  - status 为 SUCCESS 时存在
 * @property {ISyncable} [local]     - status 为 CONFLICT 时存在
 * @property {ISyncable} [remote]    - status 为 CONFLICT 时存在
 */

/**
 * ISyncable 接口约定：所有需要同步的业务对象必须满足此结构
 * @typedef {Object} ISyncable
 * @property {string}  id       - 全局唯一 ID
 * @property {string}  type     - 对象类型 (如 'Bookmark')
 * @property {number}  version  - 版本号，每次修改 +1
 * @property {boolean} deleted  - 软删除标记
 * @property {function(): string}               getHashInput - 返回用于计算哈希的标准化字符串
 * @property {function(ISyncable): MergeResult} merge        - 合并逻辑
 */

// 示例：Bookmark 的 ISyncable 实现（供业务直接参考）
export function createBookmark({ id, url, title, tags = [] }) {
  return {
    id,
    type: 'Bookmark',
    version: 1,
    deleted: false,
    url,
    title,
    tags,

    getHashInput() {
      // 只取影响业务语义的字段，确保哈希稳定
      return JSON.stringify({ id: this.id, url: this.url, title: this.title, tags: this.tags });
    },

    merge(remote) {
      // 简单字段合并策略：非冲突字段合并，冲突字段交由用户处理
      const conflicts = [];
      const resolved = { ...this };

      if (remote.url !== this.url) conflicts.push('url');
      if (remote.title !== this.title) conflicts.push('title');
      // tags 合并去重
      resolved.tags = Array.from(new Set([...(this.tags || []), ...(remote.tags || [])]));

      if (conflicts.length) {
        return { status: 'CONFLICT', local: this, remote };
      }

      resolved.version = Math.max(this.version || 0, remote.version || 0) + 1;
      return { status: 'SUCCESS', resolved };
    },
  };
}
```

#### 2. `json-git-lite/storage/Database.js`
**职责**：封装底层存储。
*   **建议**：在 Chrome 插件中，由于 Service Worker 的生命周期限制，推荐使用 **IndexedDB**（通过 `idb` 库封装）或者 **SQLite WASM**（如果你追求极致性能且能接受加载时间）。
*   **功能**：提供 `saveObject()`, `getCommit()`, `getHead()` 等原子操作。

#### 3. `json-git-lite/network/Protocol.js`
**职责**：定义 P2P 握手的完整消息格式（用 JSDoc typedef 约定结构）。

```javascript
/**
 * @typedef {Object} HandshakeReq
 * @property {string} head - 本地 HEAD hash。首次同步时为 GENESIS_HASH（'0'.repeat(64)），永远不为 null
 */

/**
 * @typedef {Object} HandshakeResp
 * @property {string[]} missingCommits - 对端缺少的 commit hash 列表
 */

/**
 * @typedef {Object} PushCheckReq
 * @property {string}   hash    - 拟推送的 merge commit hash
 * @property {string[]} parents - 父节点 hash 列表
 */

/**
 * @typedef {Object} PushCheckResp
 * @property {boolean} allowed  - 是否允许推送
 * @property {string}  [reason] - 拒绝原因
 */

// 消息 action 常量
export const ACTIONS = {
  HANDSHAKE_REQ:   'HANDSHAKE_REQ',
  HANDSHAKE_RESP:  'HANDSHAKE_RESP',
  PULL_REQ:        'PULL_REQ',
  PULL_RESP:       'PULL_RESP',
  PUSH_CHECK_REQ:  'PUSH_CHECK_REQ',
  PUSH_CHECK_RESP: 'PUSH_CHECK_RESP',
  PUSH_DATA:       'PUSH_DATA',
};
```

#### 4. `json-git-lite/engine/SyncEngine.js`
**职责**：大脑。
*   它持有 `Database` 实例和 `Peer` 实例。
*   对外暴露三个操作，语义严格区分：

| 方法 | 语义 | 说明 |
|---|---|---|
| `commitChange(obj)` | 本地提交 | 业务层数据变了，生成一个新 Commit，parent 指向当前 HEAD |
| `pull(url)` | 拉取 | 从远端拉取本地缺少的 commits，执行合并（可能触发冲突挂起） |
| `push(url)` | 推送 | **push 成功的充要条件：远端 HEAD 是本地 HEAD 的祖先**（即本地历史严格领先于远端）。远端验证通过后执行 fast-forward，无需合并。若远端有本地没有的 commits 则直接拒绝，提示"请先 pull"。 |
| `sync(url)` | 完整同步 | `pull(url)` → 等待冲突解决 → `push(url)` 的组合操作，是常见的一键同步入口 |

> **冲突解决后的续流**：`ConflictResolver.resolve()` 完成后，引擎自动调用 `push(url)`，不需要用户再次触发。

### 🔗 如何与原有业务集成？

假设你原来有一个“笔记”功能，集成步骤如下：

#### 第一步：改造业务对象
让你的 `Note` 对象满足 `ISyncable` 约定。

```javascript
// app/models/Note.js

/**
 * 创建一个满足 ISyncable 约定的 Note 对象
 * @param {string} id
 * @param {string} title
 * @param {string} content
 * @returns {ISyncable}
 */
export function createNote(id, title, content) {
  return {
    id,
    type: 'Note',
    version: 1,
    deleted: false,
    title,
    content,

    getHashInput() {
      return JSON.stringify({ id: this.id, title: this.title, content: this.content, version: this.version });
    },

    merge(remote) {
      // 简单策略：直接标记冲突，交给用户处理
      return { status: 'CONFLICT', local: this, remote };
    },
  };
}
```

#### 第二步：在 Service Worker 中初始化引擎
在 `background.js` 中初始化单例。

```javascript
import { SyncEngine } from './json-git-lite/engine/SyncEngine.js';
import { Database } from './json-git-lite/storage/Database.js';

// 初始化单例
const db = new Database();
const syncEngine = new SyncEngine(db);

// 监听来自 Popup 的同步请求
chrome.runtime.onMessage.addListener((msg, sender, sendResponse) => {
  if (msg.type === 'TRIGGER_PULL') {
    syncEngine.pull(msg.peerUrl).then(() => {
      sendResponse({ status: 'success' });
    });
    return true;
  }
  if (msg.type === 'TRIGGER_PUSH') {
    syncEngine.push(msg.peerUrl).then(() => {
      sendResponse({ status: 'success' });
    });
    return true;
  }
  if (msg.type === 'TRIGGER_SYNC') {
    syncEngine.sync(msg.peerUrl).then(() => {
      sendResponse({ status: 'success' });
    });
    return true; // 保持消息通道开放（异步 sendResponse 必须）
  }
  if (msg.type === 'RESOLVE_CONFLICT') {
    const { conflictId, strategy, data, peerUrl } = msg;
    // 文档示例：调用 ConflictResolver.resolve 后自动尝试 push
    syncEngine.conflictResolver.resolve(conflictId, strategy, data)
      .then(() => {
        // 如果提供了 peerUrl，则尝试续传（push）
        if (peerUrl) return syncEngine.push(peerUrl);
      })
      .then(() => sendResponse({ status: 'resolved' }))
      .catch(err => sendResponse({ status: 'error', message: String(err) }));
    return true;
  }
});
```

#### 第三步：在 UI 中调用
在 `popup` 页面中，当用户点击“同步”按钮时：

```javascript
// 发送消息给后台
chrome.runtime.sendMessage({ type: 'TRIGGER_SYNC', peerUrl: 'ws://192.168.1.5:8080' });
```

### 💡 集成到浏览器插件的注意事项

1.  **权限配置 (`manifest.json`)**：
    *   你需要申请 `"storage"` 权限（用于存数据）。
    *   你需要申请 `"websocket"` 或 `"host_permissions"`（用于 P2P 连接，例如 `"<all_urls>"` 或具体的 IP 段）。

2.  **Service Worker 保活**：
    *   Chrome MV3 的后台是临时的。如果同步正在进行中（P2P 连接中），浏览器可能会杀掉后台。
    *   **解决方案**：在 `SyncEngine` 中保持一个 `keep-alive` 的定时器，或者使用 `chrome.alarms` 来确保同步任务不被意外中断。

3.  **UI 反馈**：
    *   同步是异步的。你需要在 `json-git-lite/utils/EventBus.js` 中实现一个事件总线。
    *   当 `ConflictResolver` 发现冲突时，发出 `CONFLICT_DETECTED` 事件。
    *   `popup` 页面监听这个事件，弹出界面让用户进行“手动合并”。

## 补充说明（协议、存储、保活、重试、测试等）

### 细化部分

下面将把实现中尚未细化的关键点写成可执行的文档说明，便于开发实现时直接参考。

1) 协议消息（完整定义）
- `PULL_REQ` { commitHash: string } — 请求指定 commit 的完整对象
- `PULL_RESP` { commit: Commit } — commit 完整数据（含 changes）
- `PUSH_CHECK_REQ` { hash:string, parents:string[] } — 预检拟推送的 merge/新 commit
- `PUSH_CHECK_RESP` { allowed: boolean, reason?: string } — 允许或拒绝推送
- `PUSH_DATA` { commits: Commit[] } — 真正的提交数据传输
- `ERROR` { code: string, message: string } — 通用错误消息

注意：所有消息使用 JSON 封装并通过 WebSocket/WSS 传输。建议在生产环境使用 WSS 并在连接层进行重连/心跳。

2) 本地存储（IndexedDB schema 建议）
- objectStore `objects` — 当前工作区（对象表）
  - keyPath: `id`
  - value: { id, type, content, version, updated_at }
- objectStore `commits` — 提交表（DAG 节点）
  - keyPath: `hash`
  - value: { hash, parents: string[], timestamp, changes }
  - index: `byTimestamp`
- objectStore `refs` — 引用表
  - keyPath: `name` （例如 `main`）
  - value: { name, target_hash }
- objectStore `conflicts` — 未决冲突列表
  - keyPath: `id`
  - value: { id, local, remote, created_at }

3) 初始化 / 数据迁移（首次启用同步时）
- 规则：首次安装时本地 HEAD 初始化为 `GENESIS_HASH`（常量：64 个 `0`）。
- 如本地已有业务数据：在第一次 `commitChange()` 时，生成以 `GENESIS_HASH` 为父的第一个 commit（工作流无需特殊迁移步骤）。
- 如果用户在设置里填写了远端同步地址：立即触发 `pull()`；`pull()` 会基于双方 HEAD 走标准握手与差异计算流程。

4) Service Worker 保活与重试策略（建议）
- 使用 `chrome.alarms` 做心跳与保活：在长连接开始时注册周期性短时闹钟（例如 5 分钟）以防 SW 被回收。
- 连接重试：采用指数退避（base 1s, factor 2，最大 1min），可配置最大尝试次数。
- 对于 `push` 被拒绝（远端不在祖先链上）：抛出可恢复错误，提示执行 `pull()` 后重试 `push()`；自动重试次数有限并上报给 UI。

5) `SyncEngine`（伪代码 / 行为规范）
- `async pull(peerUrl)`:
  1. connect(peerUrl)
  2. send HANDSHAKE_REQ { head: localHead }
  3. receive missing list -> for each hash request PULL_REQ -> store temporary
  4. apply commits: `applyCommits()`（会触发 merge/conflict 检测）
  5. if conflicts -> emit `NEEDS_MERGE` and stop
  6. return status
- `async push(peerUrl)`:
  1. connect(peerUrl)
  2. prepare candidate head (local HEAD)
  3. send PUSH_CHECK_REQ { hash: candidate, parents: candidate.parents }
  4. if allowed -> send PUSH_DATA { commits: missingForPeer }
  5. if refused -> return error "NEED_PULL"
- `async sync(peerUrl)`:
  1. await pull(peerUrl)
  2. if no conflicts -> await push(peerUrl)
  3. return overall result

6) 冲突处理与 UI 流程
- 冲突检测在 `applyCommits()` 时进行，`ConflictResolver` 将创建 `conflict` 项并在 `conflicts` store 中存档。
- 引擎发出 `CONFLICT_DETECTED` 事件（通过 `EventBus`），附带冲突列表和冲突 id。
- `popup` 打开冲突界面，用户可选择 `LOCAL` / `REMOTE` / `MANUAL` 编辑生成最终对象。
- 用户一旦解决（调用 `resolveConflict`），引擎会：生成合并 commit（parents: [localHead, remoteHead]）、保存到 `commits`，并自动触发 `push(peerUrl)` 尝试继续同步。

7) `ISyncable` 示例（Note / Bookmark）
- 文档中已包含 `createNote()` 示例；建议再补 `createBookmark()`：
  - 字段：`id, type='Bookmark', url, title, tags, version, deleted`
  - `getHashInput()` 只序列化 `id,url,title,tags` 等核心字段
  - `merge(remote)` 默认策略：字段级合并（非冲突字段合并），冲突字段报告 `CONFLICT`。

8) 安全、鉴权与完整性建议
- 强制使用 `wss://` 以保护传输层。若需要权限管理，建议引入短期 token（通过中央授权/用户设备 pairing）。
- 可选：对 Commit 做签名（HMAC 或公私钥签名）以防劫持和伪造。

9) 错误处理与重试策略（详版）

错误类型分类：
- 临时网络错误（网络抖动、连接超时、断线） — 可重试。
- 服务端/远端逻辑拒绝（`NEED_PULL`、权限不足） — 需要特定处理流。
- 存储错误（IndexedDB quota、事务失败） — 可能需用户介入或清理。
- 永久失败（无效参数、认证失败） — 不应重试，需上报并停止。

重试策略要点：
- 使用指数退避（exponential backoff）并加随机抖动（jitter）以避免雪崩。
- 明确最大重试次数与最大退避上限（cap）。
- 对于 `push` 被拒（远端非祖先），触发 `pull()` 后再重试 `push()`；重试次数较少（例如 3 次），若仍失败则上报给 UI 要求人工干预。
- 把重试任务持久化（IndexedDB 的 `retryQueue` objectStore）以便 Service Worker 重启后恢复。

默认参数建议：
- baseDelay = 1000 ms
- factor = 2
- maxDelay = 60000 ms
- maxAttempts = 8
- jitter = 0.5 (随机 0..0.5*delay)

通用重试包装器（伪代码）：

async function retryWithBackoff(fn, opts = {}) {
  const base = opts.base || 1000;
  const factor = opts.factor || 2;
  const cap = opts.maxDelay || 60000;
  const maxAttempts = opts.maxAttempts || 8;
  for (let attempt = 1; attempt <= maxAttempts; attempt++) {
    try {
      return await fn();
    } catch (err) {
      if (isPermanentError(err)) throw err;
      if (attempt === maxAttempts) throw err;
      const delay = Math.min(base * Math.pow(factor, attempt - 1), cap);
      const jitter = Math.random() * (delay * (opts.jitter || 0.5));
      await sleep(delay + jitter);
    }
  }
}

Service Worker 专用：Alarm 驱动的重试队列
- 在 IndexedDB 中维护 `retryQueue`，条目包含 `{ id, action, payload, attempts, nextAttemptAt }`。
- 发生可重试错误时，将任务入队并调用 `chrome.alarms.create('retry-check', { periodInMinutes: 1 })`（或更精细化的调度）。
- 在闹钟触发（`chrome.alarms.onAlarm`）或 SW 启动时，处理所有 `nextAttemptAt <= Date.now()` 的队列项，按 `retryWithBackoff` 逻辑执行并更新 attempts/nextAttemptAt；失败且 attempts 超限则标记为 `failed` 并上报 UI。

### push 被拒（`NEED_PULL`）工作流：

1. 接收到 `PUSH_CHECK_RESP { allowed: false, reason: 'NEED_PULL' }`。
2. 自动执行一次 `pull(peerUrl)`（非无限重试，仅 1-3 次，带短延迟）。
3. 若 `pull` 导致冲突 -> 发出 `CONFLICT_DETECTED`，等待用户解决；解决后由用户触发或自动尝试 `push`（有最大尝试次数）。
4. 若 `pull` 成功且无冲突 -> 重新执行 `push`。

长拉取（大量 commits）策略：
- 分块拉取（例如 100 commit/批），每批落盘并更新进度到 `syncProgress` store，允许在 SW 被回收后从上次进度继续。

幂等性与去重：
- 所有 Commit 由 SHA-256 hash 唯一标识；在 push 重试中仅向对端发送对端未确认的 commit 列表。
- 所有网络请求可附带 `requestId`（UUID）以便对端做幂等处理或日志去重。

监控与上报：
- 对于连续失败（例如同一个 peer 失败超过 N 次），在 `EventBus` 发出 `PEER_UNREACHABLE` 事件并在 UI 提示用户。

示例：闹钟处理伪代码

chrome.alarms.onAlarm.addListener(async (alarm) => {
  if (alarm.name !== 'retry-check') return;
  const due = await db.getDueRetries(Date.now());
  for (const task of due) {
    try {
      await retryWithBackoff(() => performTask(task));
      await db.removeRetry(task.id);
    } catch (err) {
      await db.incrementAttempt(task.id);
      if (db.getAttempts(task.id) > MAX_ATTEMPTS) {
        await db.markFailed(task.id, err.message);
        EventBus.emit('RETRY_FAILED', task);
      }
    }
  }
});

安全提示：在重试队列中不要存放敏感明文凭据；如果需要凭据，请把凭据以短期 token 引用（或存安全存储），并在重试时动态注入。

10) 存储管理与 GC 策略
- 提交表可能随时间增长，建议支持两种清理策略：
  - 保留最近 N 个 commit 或保留最近 M 天
  - 周期性生成“快照” commit（将当前对象表打包为 single-snapshot commit），并删除被快照覆盖的旧细粒度 commits

11) 测试计划（建议）
- 单元测试：`DAGManager.hasAncestor`、`findLCA`、`createCommit`、`merge`。
- 集成测试：模拟两个 peer 的完整握手/拉取/推送流程（含冲突场景）。
- 手动验收：在局域网通过两个浏览器实例测试互通性、冲突和自动恢复。

12) 打包 / manifest 注意
- 继续使用原生 JS（无需 TypeScript 编译链）或如需 TypeScript 则在项目中加入构建步骤（`tsc`/`vite`）并把产物放到 `dist/`，`manifest.json` 指向 `dist/background.js`。
- `manifest.json` 必须包含 `host_permissions`（或明确列出对等节点地址）以及 `storage` 权限。

13) Peer 发现与部署建议
- 简单方案：用户手动输入 `ws://host:port`（最可靠，适合小众 P2P 场景）。
- 局域网自动发现：mDNS/Bonjour（需额外实现或本地代理）。
- 大规模或跨网段：使用一个轻量中继/信令服务器（可选），用于转发或做 WebRTC 信令。
